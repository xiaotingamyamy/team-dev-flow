# 团队 AI 研发工作流 Prompt 与运行记录

版本：1.2。适合团队在不同项目中处理缺陷与小范围功能交付，覆盖页面、接口、数据和状态流程。入口是一个问题、一条调用或操作路径、一个可验收结果。大型迭代沿用项目已有研发流程，本资产组织其中的具体任务闭环。

## 日常启动

```text
使用 $team-dev-flow 处理下面的任务。
项目和子工程：[项目名称 + 子工程目录，未知请先定位]
模式：[仅分析 / 梳理方案 / 实现并验证]
入口：[页面操作 / API 请求 / 任务触发 → 预期结果]
现象：[实际发生什么；附截图或日志时标记平台、版本]
预期：[具体行为和验收场景]
范围：[允许改哪些工程；必须保留什么]
先记录本次基线和验收标准，再按风险选择轻量或完整流程。
沿入口、数据来源、状态变更和展示定位根因；区分事实与假设。
实现后说明已验证、未验证和当前交付状态，并更新运行记录。
```

项目上下文足够时可以只说：“使用 $team-dev-flow，当前项目从列表进入编辑页后表单数据未回显，先分析。”缺省参数由已知上下文补齐，不为了填表反复提问。

## 把反复追问前置

| 过去常问 | 一次说清的提问方式 |
|---|---|
| 这个功能在哪个项目 | 从入口事件定位实际宿主、SDK、服务与子工程，列证据后再选改动位置 |
| 为什么带不到这个页面 | 对比来源、接口字段、映射、快照和最终绑定，找首次丢失的位置 |
| 这个接口到底做了什么 | 说明何时读取、何时写入、版本何时推进，追到下游调用而非只看 Controller |
| 返回后为什么还是新内容 | 检查草稿与正式数据、普通返回与右滑、再次进入、取消后的副作用 |
| 是否已经实现 | 分别回答源码、服务联调、设备验收、版本发布的状态 |
| 是否复用、与设计一致吗 | 先比较组件来源与各状态，再用运行截图检验尺寸与交互 |

## 三个常用追问模板

诊断：
```text
先不改代码。按入口 → 调用 → 字段映射 → 状态 → 展示列出证据，
分别给出确定原因、待验证假设、最小验证动作。核对字段真正由哪一层负责。
```

需求更新：
```text
最新规则为：[新规则]，替代：[旧规则]。
请重新读取当前实现，只更新受影响方案、代码和验收项；
已有授权内继续完成，不沿用失效结论。
```

验收：
```text
按最初验收场景核查本次改动。测试通过和设备通过分别报告；
若无法验证，列缺少的环境和具体步骤，不写“全部完成”。
检查范围外改动，给出最终交付状态和运行记录。
```

## 每次运行记录

复制后填写，未知保留“未知”。日志中的业务账号、手机号和令牌需脱敏。

```text
任务编号：B01 或 W01（B=常规流程基线，W=新工作流）
模式与版本：常规流程 / team-dev-flow 1.2
任务名称及会话链接：
项目 / 子工程 / 分支或提交：
任务负责人 / 验收人：
跨模块依赖及负责人（如有）：
类别：界面 / 接口 / 数据契约 / 状态流程 / 运行环境
规模：涉及工程数、入口数、平台数
开始前记录时间：
现象与预期：
开始前已知检查结果：
验收项及预期观察：
代码/接口/需求证据版本：
开始 / 完成时间：
AI 回合历时（可得时）：
人工有效工时（人工填写，分钟）：
等待环境或确认时间（单列）：
首轮交付时间：
首轮验收：通过 / 不通过 / 未执行
返工：次数、分钟、原因、证据
原因分类：AI错误 / 需求变更 / 接口变更 / 环境 / 新问题 / 未知
已验证：
未验证及下一步：
最终验收时间与结论：
本次可复用规则或反例：
```

先收集 B01 至 B03，再连续记录 W01 至 W03；按类别和规模配对。若已有可靠的同类基线可直接引用，不需人为重复工作。不能撤掉质量检查制造“旧流程”。本次历史摘录仅是辅助参照。

同类人工工时改善比例 =（基线人工工时中位数 − 新流程人工工时中位数）/ 基线人工工时中位数。
首次通过率 = 首轮验收通过数 / 实际执行首轮验收数，同时报告未验收数。
返工只统计首次实现后的修正，需求变更另列；同一纠正事件不要按消息条数重复计数。
样本小只作团队改进参考，不做因果或总体效率结论。

每 3 次真实使用做一次复盘：最常补充的问题是什么，哪条规则避免了可证明的错误，哪条增加了负担。每次只改必要规则，记录版本、触发证据、改动与下一轮检验项。
